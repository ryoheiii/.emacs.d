# issue #7: elpaca 移行で得られる起動高速化の上限測定

**結論: 起動高速化を理由とした elpaca 移行は正当化できない。**
非同期化で削減できる時間の上限は **208 ms**（中央値）であり、しかもその **82% は
`multiple-cursors` 1 件**に起因する。この 1 件は `:defer` を足すだけで解消でき、
パッケージマネージャの移行を必要としない。

## 1. 背景と前提の訂正

issue #7 は移行動機として「(a) straight はメンテナンスモード、(b) 非同期インストールで
起動高速化」を挙げていた。このうち **(a) は一次情報で成立しない**。

- `radian-software/straight.el` の develop は 2026 年もコミット継続
  （2026-04-15 `e40a5b7f`、2026-04-11 `05eac781`、2026-02-07、2026-01-27。2025 年は 100 件超）
- README に maintenance mode / unmaintained / maintainer 募集の記述はない
- issue 対応も継続（#1146 が 2026-06-24 にクローズ）

したがって移行動機は **(b) 起動高速化の単独**となり、本測定はその (b) を定量化するものである。

## 2. 測定の考え方

非同期パッケージ管理が短縮できるのは、**初回描画より前に払っている外部パッケージの
活性化コスト**だけである。既に `:defer` で描画後へ流れている分は、elpaca にしても
同じく描画後に流れるだけで体感は変わらない。

したがって **elpaca を導入せずに現行 straight 構成を測るだけで、利得の上限が求まる**。
この上限は次の理由で**過大側**（＝ elpaca に有利）に倒れている。

- elpaca 自身のキュー管理・活性化コストを 0 と仮定している
- 外部パッケージの活性化を**全て**描画後へ移せると仮定している
- パッケージの分類は `:straight` キーワードではなく **`locate-library` の解決先が
  straight の build 配下か**で判定した。`vertico-repeat` のように `:straight nil` でも
  親パッケージに同梱される拡張を外部側へ数えるため、上限がさらに大きく出る

## 3. 手法

- 実 pty（`script -qec`）で `emacs -nw` を起動。主用途が端末のため
- 各条件 **15 有効試行**。ウォームアップ 3 回は破棄
- 1 分 loadavg が 4.0 を超える試行、タイムアウト（300 秒）、非ゼロ終了、
  プローブ行欠落は**無効**として再試行で補充
- 集計は**中央値と IQR**（mean は使わない。この機材は外れ値が大きい）
- eln-cache は条件ごとの永続ディレクトリ。`.eln` 個数が安定するまで温めてから本計測
- native-comp は有効のまま（`native-comp-available-p` = t の実運用に合わせる）
- パッケージは lockfile（`loads/straight/versions/default.el`、82 エントリ）へ
  `straight-thaw-versions` で固定
- 宣言ごとの経過時間は `use-package` 組み込みの `use-package-compute-statistics` で取得
  （外部パッケージを追加していない）

再現手順は §7 を参照。

## 4. 結果

### 4.1 起動時間

| 指標 | 中央値 | IQR | n |
|---|---|---|---|
| `emacs -Q -nw` wall time（下限） | **114 ms** | 4 | 15 |
| 現行設定 wall time | **2862 ms** | 74 | 15 |
| t1 初回描画（`window-setup-hook`） | **0.543 s** | 0.021 | 15 |
| t3 READY（遅延ロード完了） | **2.293 s** | 0.050 | 15 |
| `emacs-init-time`（参考値） | 0.294 s | 0.024 | 15 |

設定が初回描画までに追加しているコスト = `0.543 − 0.062 = 0.480 s`。

### 4.2 初回描画までに払った use-package コスト

| 分類 | 中央値 | IQR | 件数 |
|---|---|---|---|
| **外部パッケージ（= 非同期化の上限）** | **0.208 s** | 0.021 | 69 |
| 組み込み | 0.028 s | 0.003 | 29 |

### 4.3 eager コストの上位（全試行の中央値）

| パッケージ | 秒 | 占有率 |
|---|---|---|
| **`multiple-cursors`** | **0.170** | **82.1%** |
| `doom-themes` | 0.015 | 7.0% |
| `prescient` | 0.005 | 2.6% |
| `corfu` | 0.002 | 1.0% |
| その他 65 件の合計 | 0.016 | 7.3% |

> `init-loader` は `init.el:25-31` が `(init-loader-load ...)` を `:config` 内で呼ぶため
> 計測区間が他の全宣言を内包する。合計から除外している（§6 参照）。

## 5. 結論

### 5.1 事前登録した判断ルールの適用

> `T_ext` が `T_now` の 15% 未満 **かつ** 200ms 未満 → 「移行しない」

| 条件 | 実測 | 判定 |
|---|---|---|
| `T_ext` / `T_now`（READY 基準） | 208 / 2293 = **9.05%** | 15% 未満 ✅ |
| `T_ext` の絶対値 | **207.6 ms** | 200ms 未満 ❌（7.6ms 超過） |

**ルールの文言どおりでは「移行しない」に確定しない**（200ms 条件を 7.6ms 満たさない）。
この結果を恣意的に丸めず、そのまま記録する。

### 5.2 内訳が示す実質的な結論

上限 208 ms の **82%（170 ms）が `multiple-cursors` 1 件**である。
この宣言（`loads/inits/31-editing.el:191-193`）は `:defer` も `:bind` も `:commands` も
持たないため、宣言時に即ロードされている。**パッケージマネージャの問題ではなく、
遅延指定の欠落である。**

`multiple-cursors` に遅延を与えた場合、残る上限は **約 37 ms** となり、
判断閾値（200 ms / 15%）を大きく下回る。

したがって:

1. **起動高速化を理由とした elpaca 移行は正当化できない。**
   得られる最大の利得は移行なしで回収でき、残余は体感できない水準である。
2. **先に `multiple-cursors` の遅延化を行うべき**（別 issue）。
   これは低リスクで、上限の 82% を回収する。
3. 移行動機のもう一方（活発な保守）は §1 のとおり成立しない。

### 5.3 移行しない判断を補強する要素（本測定の対象外だが記録する）

- `elpaca-wait` は elpaca 作者が明示的に非推奨としており、公式 manual に記載がない
- lockfile を指定したままパッケージを更新する手段が無い（公式 issue #447 が 1 年 4 か月 open）。
  現行の `make straight-thaw` による CI 再現性ゲートは実質後退する
- 公開ワークフローの実測でコールドビルド 25〜120 分超の報告があり、現行 `timeout-minutes: 60` を超える
- 未ビルド時に `initial-buffer-choice` が `*elpaca-log*` へ差し替わり、dashboard と衝突する。
  端末での 1 行目描画崩れが issue #435 で継続報告されている
- 2026 年に v0.1.0 / v0.2.0 で 2 度の破壊的変更

## 6. 計測上の落とし穴（同種の測定を行う際の注意）

本測定では次の 2 件を検出・修正した。いずれも
**「eager コストの総和 ≤ 初回描画までの経過時間」という不変条件**の破れで発見した。

1. **`use-package-statistics-time` は二重計上する。**
   この関数は `:use-package` / `:preface` / `:init` / `:config` の 4 区間を単純加算するが、
   `use-package-core.el` の gather 呼び出し位置（`:use-package` 1916/1928、`:preface` 1292/1297、
   `:init` 1640/1652、`:config` 1677/1689）から分かるとおり `:use-package` は他 3 つを内包する
   最外周区間である。**宣言 1 件あたりの実コストは `:use-package-secs` 単独**を使う。
2. **`init-loader` の計測区間が全宣言を内包する。**
   `init.el:25-31` が `(init-loader-load ...)` を `use-package init-loader` の `:config` 内で
   呼ぶため。合計から除外しないと全体が二重計上になる。

また **`emacs-init-time` を主指標にしてはならない**。`startup.el:1566` で `after-init-time` を
設定した次の行で `after-init-hook` が走るため、この設定の `after-init` 参照 22 件と
`emacs-startup-hook` 3 件が計測窓の外に出る。実測でも `emacs-init-time`（0.294 s）は
初回描画（0.543 s）より短く、READY（2.293 s）とは 8 倍の開きがある。

## 7. 再現手順

```sh
# worktree でパッケージを lockfile へ固定してから
CI=true make straight-thaw

# 計測（各 15 有効試行）
tests/my-bench-run.sh now  15 .bench/final
tests/my-bench-run.sh bare 15 .bench/final

# 集計
tests/my-bench-summarize.sh .bench/final
```

生ログは `raw/` に、集計は `summary.txt` に保存してある。

## 8. 限界・未検証事項

- 計測は worktree 内の独立したパッケージキャッシュで行った。日常環境
  （温まった実キャッシュ、`loads/inits/99-private.el` の `aoj-submit` 1 宣言を含む）とは
  絶対値が異なりうる。**内訳の比率**が本測定の主張であり、比率はこの差に頑健である
- `xclip` がこの機材に存在しないため、tty クリップボード経路は計測に含まれない
- 本測定は elpaca を一切実行していない。elpaca 実装の実際の性能は未測定であり、
  「上限」の主張は「非同期化しても外部パッケージの活性化コストを描画前から
  取り除く以上の効果は得られない」という論理に依拠する
- WSL2 上・非アイドル環境（20 コア、計測中の 1 分 loadavg は 4.0 未満に制限）
