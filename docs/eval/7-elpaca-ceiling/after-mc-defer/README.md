# multiple-cursors 遅延化の効果測定（追試）

親ディレクトリの測定で「上限 208 ms の 82% が `multiple-cursors` 1 件」と判明したことを受け、
`loads/inits/31-editing.el` の同宣言へ `:defer t` を与えた前後を**同一ハーネス・同一条件**で比較した。

## 結果（各 15 有効試行、中央値）

| 指標 | 修正前 | 修正後 | 改善 |
|---|---|---|---|
| wall time | 2862 ms | **2711 ms** | **−151 ms** |
| t1 初回描画 | 0.543 s | **0.477 s** | **−66 ms** |
| t3 READY | 2.293 s | **2.170 s** | **−123 ms** |
| 外部パッケージ eager コスト | 0.208 s | **0.174 s** | −34 ms |
| `multiple-cursors` の eager コスト | 0.170 s | **0.138 s** | −32 ms |

健全性検査（eager 総和 ≦ t1）は 15/15 通過。

## 予測との差異と、その原因

当初は「170 ms のほぼ全量が回収できる」と見積もったが、**実際に消えたのは約 32 ms** だった。
`multiple-cursors` の宣言は遅延後もなお **138 ms** を要する。内訳を切り分けた結果は次のとおり。

| 内訳 | 実測 | 備考 |
|---|---|---|
| `:custom`（`customize-set-variable`） | 15.5 ms | 遅延中でも実行される。本体はロードしない（`featurep` は nil のまま） |
| `:init`（`defvar-keymap :repeat t` × 24 + `global-set-key`） | 0.1 ms | 実質ゼロ |
| **残余（`:straight t` の処理）** | **約 122 ms** | 差分による帰属。straight のパッケージ登録と autoload 読み込み |

**遅延指定は本体のロードを止めるが、パッケージマネージャの登録処理は止めない。**
`(featurep 'multiple-cursors)` は起動直後 nil であり（`my-test-packages-deferred-features` で固定）、
遅延自体は正しく効いている。

一方、観測される起動時間の改善（t1 −66 ms、wall −151 ms）は eager コストの減少（−34 ms）より
大きい。本体のロードが起動経路から完全に消えたことで、`use-package` の計測窓の外にあった
コスト（ライブラリ読み込みに伴う I/O・native-comp 経路など）も同時に減ったためと考えられる。

## issue #7 の結論への影響

**結論は変わらない（移行しない）。むしろ判断は明確になった。**

事前登録ルール「`T_ext` が `T_now` の 15% 未満**かつ** 200 ms 未満なら移行しない」の適用:

| 時点 | `T_ext` | 対 READY | 200 ms 判定 | ルールの帰結 |
|---|---|---|---|---|
| 修正前 | 207.6 ms | 9.05% | ❌ 7.6 ms 超過 | 確定しない |
| **修正後** | **173.7 ms** | **8.0%** | ✅ | **「移行しない」で確定** |

ただし当初の説明「上限の 82% は遅延指定漏れで、移行なしで回収できる」は**不正確**だった。
正確には次のとおりであり、記録として訂正する。

- 遅延化で直接回収できたのは約 32 ms（上限の 15%）
- 残る `multiple-cursors` の 122 ms は `:straight t` の登録処理であり、
  **これは原理的には非同期パッケージ管理が起動経路から外せる種類のコストである**
- それでも残余を含めた上限 174 ms は、事前登録した判断閾値（200 ms / 15%）を下回る。
  したがって移行の正当化には至らない

## 今後の候補（本タスクの範囲外）

`multiple-cursors` の `:straight t` 登録が約 122 ms を要するのは、他の外部パッケージ
（1〜15 ms）と比べて突出している。原因の特定は未実施であり、これを削減できれば
上限はさらに下がる。パッケージマネージャの移行より先に検討する価値がある。


## ⚠ 訂正（この文書の数値は計測環境に汚染されている）

本文書の「遅延後もなお 138 ms を要し、うち約 122 ms は `:straight t` の登録処理」という
記述は**誤り**である。worktree 内のコピーされたパッケージキャッシュによるアーティファクトだった。

実環境・同一ハーネスで測り直した確定値は `../CORRECTION.md` を参照すること。
要点は次のとおり。

- `multiple-cursors` の宣言コストは遅延化により **0.180 s → 0.00017 s** とほぼ全量が消えた
- 外部パッケージ eager コスト（上限）は **0.218 s → 0.035 s**
- `:straight t` の登録処理は **1.3 ms 程度**であり、122 ms を要してはいない
