# 訂正: 計測環境による汚染と、確定した数値

`after-mc-defer/README.md` に記した「`multiple-cursors` は遅延後もなお 138 ms を要し、
その約 122 ms は `:straight t` の登録処理である」という記述は**誤りである**。

実際には **`:straight t` の登録処理は 1.3 ms 程度**であり、遅延化によって
`multiple-cursors` の宣言コストは **ほぼ全量が消えている**。

## 何が起きたか

親ディレクトリと `after-mc-defer/` の測定は、いずれも **git worktree 内**で実行した。
その worktree の straight キャッシュは実体からの `cp -a` コピー（1.9 GB、新しい inode）であり、
実環境（メインチェックアウトの実キャッシュ）とは条件が異なっていた。

この差は特に**修正後**の測定に出た。同じ宣言のコストを条件を変えて測った結果:

| 計測条件 | `multiple-cursors` の宣言コスト |
|---|---|
| `straight-use-package` 単体（実キャッシュ） | 1.3 ms |
| バッチで全設定ロード後（実キャッシュ） | 0.27 ms |
| 実 pty・一時ルート（実キャッシュ） | 0.17 ms |
| ベンチ本体・メインチェックアウト（8 試行） | 0.00017 s（安定） |
| **worktree（コピーキャッシュ）** | **138 ms** |

修正**前**の値は worktree（208 ms）と実環境（218 ms）でほぼ一致しており、
汚染は主に修正後の測定に現れた。**機序は完全には特定できていない。**

## 確定した数値（実環境・同一ハーネス・各 5 試行の中央値）

`tests/my-bench-run.sh` をメインチェックアウトで実行し、修正前は
`git checkout c681783 -- loads/inits/31-editing.el` で作業ツリーを一時的に戻して測定した
（測定後に復元済み）。ハーネス・キャッシュ・環境はすべて同一。

| 指標 | 修正前 | 修正後 | 改善 |
|---|---|---|---|
| wall time | 2571 ms | **2380 ms** | **−191 ms** |
| t1 初回描画 | 0.551 s | **0.376 s** | **−175 ms** |
| t3 READY | 2.128 s | **1.937 s** | **−191 ms** |
| 外部パッケージ eager コスト（＝上限） | 0.218 s | **0.035 s** | **−183 ms** |
| `multiple-cursors` の eager コスト | 0.180 s | **0.00017 s** | **−180 ms** |

健全性検査（eager 総和 ≦ t1）は全試行通過。

## どの主張が正しかったか

| 主張 | 判定 |
|---|---|
| 「上限の 82% が `multiple-cursors` 1 件」（親 README） | **正しい**（実環境で 180/218 = 82.6%） |
| 「遅延化で残る上限は約 37 ms」（親 README の予測） | **正しい**（実測 35 ms） |
| 「遅延後も 138 ms 残り、うち 122 ms は straight の登録処理」（`after-mc-defer/`） | **誤り**。worktree 環境のアーティファクト |
| 「遅延化で直接消えたのは約 32 ms（上限の 15%）」（`after-mc-defer/`） | **誤り**。実際は約 180 ms（上限の 82%） |

## issue #7 の結論への影響

**結論は変わらない（移行しない）。根拠はさらに強くなった。**

事前登録ルール「`T_ext` が `T_now` の 15% 未満**かつ** 200 ms 未満なら移行しない」:

| 時点 | `T_ext` | 対 READY | 200 ms 判定 | ルールの帰結 |
|---|---|---|---|---|
| 修正前 | 218 ms | 10.2% | ❌ | 確定しない |
| **修正後** | **35 ms** | **1.8%** | ✅ | **「移行しない」で確定** |

非同期パッケージ管理が起動経路から外せる時間は、現状で最大 **35 ms** しかない。
移行に伴う lockfile 運用の後退・CI 時間の増大・tty 描画リスクを正当化できない。

## 教訓（今後この計測を行う場合）

- **worktree で計測しない。** パッケージキャッシュを実体からコピーすると、
  実環境と異なる結果が出ることがある。メインチェックアウトの実キャッシュで測る
- 修正前後を比較する場合は、`git checkout <rev> -- <file>` で作業ツリーを一時的に戻し、
  **同一ハーネス・同一キャッシュ**で測る（`my-bench-run.sh` は作業ツリーの差分を取り込む）
- 単一パッケージへ大きなコストが帰属した場合は、`straight-use-package` 単体・バッチ・実 pty の
  3 経路で裏を取る。1 経路の数値を信用しない
